# SentiScope AI — Security Requirements

## 1. Security objectives

Protect application availability, uploaded datasets, user-submitted text, stored metadata, model artifacts, and configuration secrets.

Apply secure defaults appropriate for an academic application. Do not claim a formal security certification or production security audit.

## 2. Threat considerations

Consider:
- Malformed or oversized text input.
- Malicious or malformed CSV files.
- CSV formula injection in exported files.
- Path traversal and unsafe filenames.
- Denial of service through excessive rows or long text.
- Cross-origin API access.
- Secret leakage through frontend bundles or logs.
- Unsafe deserialization of model artifacts.
- Accidental persistence or exposure of user text.
- SQL injection and unsafe dynamic queries.
- Dependency vulnerabilities.

## 3. Input validation

### Text input
- Reject empty or whitespace-only strings.
- Enforce a documented maximum character/token limit.
- Validate content type and request size.
- Do not assume that user text is safe to render as HTML.
- Render user text as escaped text, never as trusted HTML.

### CSV uploads
- Accept only the expected CSV format in the initial version.
- Validate extension and content; do not trust filename alone.
- Enforce maximum file size, row count, and column count.
- Validate encoding and handle malformed rows.
- Require a valid selected text column.
- Reject unsupported or ambiguous schemas with clear errors.
- Use generated server-side temporary filenames.
- Store uploads outside publicly served directories.
- Delete temporary files after processing according to the retention policy.

### Export protection
- Escape values beginning with spreadsheet formula characters such as `=`, `+`, `-`, or `@` when producing CSV exports.
- Set safe download filenames.
- Do not expose internal filesystem paths.

## 4. API security

- Use Pydantic schemas for all request bodies.
- Set request-size and processing limits.
- Configure CORS with explicit allowed origins; do not use wildcard origins with credentials.
- Use appropriate HTTP status codes.
- Avoid leaking stack traces, secrets, database details, or internal paths.
- Add rate limiting if the deployment environment supports it.
- Keep health endpoints minimal.
- Validate query parameters and pagination bounds.

## 5. Secrets and configuration

- Store secrets only in server-side environment variables or a suitable secret manager.
- Never put private secrets in `VITE_*` variables or frontend source.
- Commit `.env.example` with placeholders only.
- Add `.env`, private keys, credentials, and local secret files to `.gitignore`.
- Rotate any credential accidentally exposed.
- Do not print environment values in logs or error responses.

## 6. Model artifact security

- Load only model artifacts generated by the trusted SentiScope AI training workflow.
- Do not accept arbitrary user-uploaded pickle/joblib/model files.
- Keep artifact paths controlled by server configuration or a trusted registry.
- Validate expected model metadata and supported labels.
- Restrict write access to model artifact directories.
- Prefer safer formats where available; if joblib/pickle is used, treat artifacts as executable trusted content.
- Record model version, checksum, training configuration, and dataset provenance where practical.

## 7. Database security and privacy

- Use parameterised ORM operations.
- Do not construct SQL queries by concatenating user input.
- Store raw text only when explicitly enabled by a clear privacy setting.
- Default history records should store minimal metadata and prediction results.
- Provide deletion for stored history if history is enabled.
- Avoid placing raw text in logs, analytics events, or error reports.
- Keep local database files out of public/static directories and version control.

## 8. Frontend security

- Render user-provided content as text.
- Avoid unsafe HTML injection APIs.
- Do not store server secrets in browser storage.
- Do not trust client-side validation alone.
- Validate all sensitive operations on the backend.
- Use secure dependency versions and review frontend packages.
- Provide clear session/privacy messaging if authentication is introduced later.

## 9. Logging and monitoring

- Log application events, failures, request identifiers, and operational metadata.
- Do not log passwords, tokens, secrets, or raw user text by default.
- Avoid returning internal exception details to users.
- Keep logs access-controlled and apply retention appropriate to the deployment.

## 10. Dependency and deployment security

- Pin or constrain dependencies using maintained manifests/lockfiles.
- Review dependencies before adding them.
- Keep runtime and libraries updated.
- Disable debug mode in deployment.
- Use HTTPS in public deployment.
- Configure trusted origins and environment-specific settings.
- Verify file persistence and model artifact storage before selecting a hosting provider.
- Do not assume a deployment platform supports large ML artifacts or persistent SQLite storage without testing.

## 11. Security testing checklist

- Empty and excessively long text requests.
- Oversized CSV upload.
- Non-CSV file renamed with `.csv`.
- Malformed CSV and invalid encoding.
- Missing text column.
- Excessive row/column count.
- CSV formula payload in export.
- Path traversal filename.
- Invalid model identifier.
- Missing/corrupt model artifact.
- CORS request from an unapproved origin.
- Error response does not reveal stack trace or secrets.
- Raw text is not persisted when privacy setting is disabled.

## 12. Incident handling

If a secret, private dataset, or sensitive user text is accidentally committed or exposed:
1. Stop further distribution.
2. Remove the exposed content from the active release.
3. Rotate affected credentials.
4. Review logs and access where possible.
5. Document the incident and corrective action.

## 13. Security acceptance criteria

- All input is validated server-side.
- Upload limits are enforced.
- Temporary uploads are not publicly accessible.
- No secrets are included in frontend bundles or committed files.
- Model loading is restricted to trusted artifacts.
- Raw text is not stored by default.
- Errors do not disclose sensitive internals.
- Security checklist tests are run and results documented.
